# Deník realizace — 2026-11-13

Daily progress is available from the full detail of an existing `installation` job under **Deník realizace → Přidat dnešní zápis**. Date and author are supplied automatically; work is required. Material text, complications/notes, next step and original JPG/PNG/HEIC photos are optional. Newest days appear first in expandable cards. A manager can correct any visible entry; an assigned worker can correct their own entries. Reading/writing retains the job's existing role, assignment, discipline and installation boundaries. No customer/garden/job is copied, and a daily save neither changes the job status nor creates/finalizes a service report or resolves a defect.

## Reused existing components

- `subWorkJob`/`workspaceJobScope`: canonical backend job authorization, including assigned colleagues and irrigation/Garden separation.
- `subscription_operations`: existing atomic operation-ID ledger prevents duplicate retries. Entry CAS versions reject stale edits, independently of the job's scheduling version.
- `service_photos`, `/api/jobs/:id/service/photos/:id`, private BUCKET objects, original-byte checks and ID/hash idempotency: existing protocol photo pipeline. Existing Google Drive photos can remain references; no Drive integration/configuration changes. New diary uploads use the existing original protocol photo pipeline and its `photoUploads`/`protocolPhotos` controls.
- Existing `serviceWork` IndexedDB object store and synchronization sender: diary records have separate keys/subtypes and cannot overwrite a service protocol. Original-photo packing is reused. Pending counts, account-switch protection, startup manifest checks, workspace recovery encryption and access revocation handle these records through their parent job ID.
- Existing per-user form drafts preserve unfinished text and selected photos. Offline saves require an already loaded authorized diary and an unexpired session/24-hour copy. Protocol and diary queues retain separate IDs during identity alias rebasing.
- Existing garden history: daily entries are nested under the original realization visit, without duplicate visits. Photos remain the same job photo references. Existing complete backups enumerate the new table automatically; privacy exports include relevant diary rows and transfer inventory recognizes the table.
- Native SwiftUI source uses `APIStore`, encrypted `APIVault`, `APIFieldsView`, `APIFilesView` (same camera/picker), binary outbox/dependencies and the existing conflict review. No web UI is embedded.

## Data/API

Append-only schema migration `0054_job_diary_entries.sql` adds one table and a job/date/ID index; no existing row is rewritten. Generated Drizzle snapshot and journal are committed. Every row retains parent job, date, work, optional fields, photo ID references, version, original author/name/time and last editor/name/time.

- `GET /api/jobs/:job/diary`: newest 50 entries, keyset cursor for older entries.
- `GET /api/jobs/:job/diary/:entry`: one authorized entry.
- `PUT /api/jobs/:job/diary/:entry`: validated date/work/photo references, expected entry version, operation ID. Only realization jobs; no destructive diary endpoint added.

## Limits

Offline mode needs an initial online load and its existing session/module access lease. Full web detail outside cached job views still requires the existing supported online path. Photos can be selected from camera/gallery; saved files open via their existing authenticated endpoint, not public links. HEIC display depends on the device. Maximum 40 photo references per entry, 25 MB per new photo, matching the existing photo route. No PDF export or automatic transfer of day text into the final service protocol was added; they remain separate records.
